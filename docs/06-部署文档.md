> 文档版本：v0.2
> 更新日期：2026-11-24
> 适用代码版本：v0.2.0
> 关联文档：[项目架构](./01-项目架构.md)｜[开发记录](./05-开发记录.md)｜[版本更新](./04-版本更新.md)

## 1. 部署范围

本文按当前仓库的真实能力编写，采用以下拓扑：

```text
教师浏览器
   │ HTTPS
   ▼
Caddy :80/:443
   ├─ 静态文件 → /srv/scorelens/app/apps/web/dist
   └─ /api/*   → 127.0.0.1:3100
                    │
                    ▼
              systemd / Node.js
              ScoreLens API
                    │
                    ▼
        PostgreSQL 16（Docker 容器）
        仅监听 127.0.0.1:5432
```

当前仓库没有 API/Web 的 Dockerfile，因此不在本文中宣称可以“一套 Compose 启动全部服务”。数据库使用 Docker Compose，API 使用 systemd，Web 使用 Caddy。该方式依赖少，适合单校测试部署和小型正式部署。

> 本文命令以 root 或具有 sudo 权限的账号执行。`scorelens.example.com` 为示例域名，必须替换为实际域名。未在 Ubuntu 24.04 实机执行前，应把本文视为待验收步骤，而不是已验证结论。

## 2. 服务器要求

| 项目 | 建议 |
| --- | --- |
| 操作系统 | Ubuntu 24.04 LTS |
| CPU / 内存 | 2 vCPU / 4GB 起步 |
| 磁盘 | 40GB SSD 起步，按备份保留量增加 |
| 网络 | 固定内网 IP 或域名；只开放 SSH、80、443 |
| 数据库 | PostgreSQL 16，由 Docker Compose 管理 |
| 运行时 | Node.js 24 LTS、pnpm 12 |
| 时区 | `Asia/Shanghai` |
| 浏览器 | 近两年 Chrome/Edge |

生产环境不要使用演示账号，不要把 5432 或 3100 端口暴露到公网。

## 3. 系统初始化

### 3.1 更新系统与安装基础工具

```bash
sudo apt-get update
sudo apt-get upgrade -y
sudo apt-get install -y curl git ca-certificates ufw
```

### 3.2 安装 Node.js 24 与 pnpm

```bash
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt-get install -y nodejs
sudo corepack enable
sudo corepack prepare pnpm@12.4.1 --activate
node --version
pnpm --version
```

预期 Node.js 主版本为 24，pnpm 与仓库 `packageManager` 字段一致。

### 3.3 安装 Docker 与 Compose

```bash
sudo apt-get install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
docker --version
docker compose version
```

### 3.4 创建部署账号与目录

```bash
sudo useradd --system --create-home --home-dir /srv/scorelens scorelens
sudo mkdir -p /srv/scorelens/app /srv/scorelens/data/uploads /srv/scorelens/backups
sudo chown -R scorelens:scorelens /srv/scorelens
sudo chmod 755 /srv/scorelens /srv/scorelens/app
```

允许应用账号管理 Docker：

```bash
sudo usermod -aG docker scorelens
```

> Docker 组权限近似 root 权限。仅将可信的运维/应用账号加入该组。重新登录 SSH 后组权限才生效。

## 4. 获取代码

把仓库克隆到 `/srv/scorelens/app`：

```bash
sudo -iu scorelens
git clone "你的仓库地址" /srv/scorelens/app
cd /srv/scorelens/app
git status
```

如果服务器已经存在代码目录，不要重复克隆，应确认工作区状态后按“版本升级”章节操作。

## 5. 配置 PostgreSQL

### 5.1 设置数据库密码

在仓库根目录创建 `.env`：

```bash
cd /srv/scorelens/app
nano .env
```

写入：

```env
POSTGRES_PASSWORD="替换为强密码"
```

数据库用户名和库名保持 `scorelens`。密码如包含 `@`、`:`、`/` 等字符，写入 API 连接串时必须做 URL 编码。

### 5.2 检查端口绑定

`docker-compose.yml` 当前将数据库绑定到 `127.0.0.1:5432`，宿主机 API 可以连接，外部网络不能直接连接。确认配置为：

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

不要改成 `5432:5432` 或 `0.0.0.0:5432:5432`。

### 5.3 启动并检查数据库

```bash
cd /srv/scorelens/app
docker compose up -d postgres
docker compose ps
docker compose exec postgres pg_isready -U scorelens -d scorelens
```

预期数据库状态为 `healthy`，`pg_isready` 返回接受连接。

## 6. 配置 API

### 6.1 创建环境变量文件

```bash
cd /srv/scorelens/app
cp apps/api/.env.example apps/api/.env
chmod 600 apps/api/.env
nano apps/api/.env
```

生产配置示例：

```env
NODE_ENV="production"
DATABASE_URL="postgresql://scorelens:URL编码后的密码@127.0.0.1:5432/scorelens?schema=public"
SESSION_SECRET="使用 openssl rand -hex 32 生成"
APP_ORIGIN="https://scorelens.example.com"
PORT=3100
UPLOAD_DIR="/srv/scorelens/data/uploads"
TZ="Asia/Shanghai"
```

生成会话密钥：

```bash
openssl rand -hex 32
```

注意事项：

- `NODE_ENV=production` 会启用 Secure Cookie，必须通过 HTTPS 访问。
- `APP_ORIGIN` 必须是实际访问域名，不要带路径或末尾斜杠。
- `SESSION_SECRET` 更换后现有登录会话会失效。
- `UPLOAD_DIR` 使用绝对路径，避免 systemd 工作目录变化导致文件位置不一致。
- `.env` 已被 Git 忽略，但仍需限制文件权限并纳入服务器备份策略。

## 7. 安装、迁移与构建

以下命令均以 `scorelens` 用户执行：

```bash
sudo -iu scorelens
cd /srv/scorelens/app
pnpm install --frozen-lockfile
pnpm --filter @scorelens/api prisma:generate
pnpm --filter @scorelens/api prisma:deploy
pnpm typecheck
pnpm build
```

说明：

1. `prisma:generate` 生成当前 schema 对应的 Prisma Client。
2. `prisma:deploy` 只应用已有迁移，不在生产环境创建新迁移。
3. `pnpm build` 会先构建 shared，再构建 API 和 Web。
4. 如果构建失败，先修复问题，不要跳过类型检查或忽略迁移直接启动。

### 7.1 测试环境可选：写入演示数据

```bash
pnpm db:seed
```

> `db:seed` 会清空并重建演示数据。只能在空的开发/测试库执行，严禁对正式学生数据执行。

当前演示账号：

| 角色 | 账号 | 密码 |
| --- | --- | --- |
| 班主任 | `wang` | `wang123` |
| 年级主任 | `director` | `director123` |
| 任课老师 | `zhang` | `zhang123` |
| 管理员 | `admin` | `admin123` |

正式部署必须通过受控初始化方式创建真实账号，不能直接沿用上述密码。

## 8. 使用 systemd 管理 API

创建服务文件：

```bash
sudo nano /etc/systemd/system/scorelens-api.service
```

写入：

```ini
[Unit]
Description=ScoreLens API
After=network-online.target docker.service
Wants=network-online.target docker.service

[Service]
Type=simple
User=scorelens
Group=scorelens
WorkingDirectory=/srv/scorelens/app/apps/api
EnvironmentFile=/srv/scorelens/app/apps/api/.env
ExecStart=/usr/bin/node /srv/scorelens/app/apps/api/dist/main.js
Restart=on-failure
RestartSec=3
TimeoutStopSec=20
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/srv/scorelens/data/uploads

[Install]
WantedBy=multi-user.target
```

启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now scorelens-api
sudo systemctl status scorelens-api --no-pager
```

查看日志：

```bash
sudo journalctl -u scorelens-api -f
```

本机健康检查：

```bash
curl -fsS http://127.0.0.1:3100/api/v1/health
```

预期：

```json
{
  "status": "ok",
  "service": "scorelens-api",
  "db": "up",
  "timestamp": "..."
}
```

如果返回 `db=down` 或 HTTP 503，先检查数据库容器、`DATABASE_URL` 和 API 日志。

## 9. 配置 Caddy

### 9.1 安装

```bash
sudo apt-get install -y caddy
sudo systemctl enable --now caddy
```

### 9.2 站点配置

```bash
sudo nano /etc/caddy/Caddyfile
```

写入：

```caddyfile
scorelens.example.com {
    encode zstd gzip

    handle /api/* {
        reverse_proxy 127.0.0.1:3100
    }

    handle {
        root * /srv/scorelens/app/apps/web/dist
        try_files {path} /index.html
        file_server
    }
}
```

替换域名后重载：

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy 会为公网域名自动申请证书。纯内网域名无法自动签发公网证书时，应由学校提供证书，或在内网明确接受 HTTP 的限制并调整 Cookie 安全策略；不要为了登录方便把生产 Cookie 改为非 Secure。

### 9.3 检查静态资源权限

Caddy 需要读取 `/srv/scorelens/app/apps/web/dist`。确认目录可被 Caddy 用户遍历：

```bash
namei -l /srv/scorelens/app/apps/web/dist/index.html
```

通常保持 `/srv`、`/srv/scorelens`、`app` 目录为 755 即可，不需要把源码目录设为 777。

## 10. 防火墙

在确认 SSH 仍可连接的前提下配置：

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
```

不要开放 5432、3100。Docker 发布端口可能绕过部分 UFW 规则，因此数据库必须保持 `127.0.0.1` 绑定，不能只依赖防火墙。

## 11. 部署验收

### 11.1 服务检查

```bash
systemctl is-active scorelens-api
systemctl is-active caddy
docker compose -f /srv/scorelens/app/docker-compose.yml ps
curl -fsS https://scorelens.example.com/api/v1/health
```

### 11.2 浏览器检查

1. 打开 `https://scorelens.example.com`，确认跳转登录页。
2. 使用测试账号登录，确认 Cookie 中 `scorelens.sid` 为 `Secure`、`HttpOnly`。
3. 验证班主任、年级主任、任课老师的数据范围。
4. 上传一个脱敏 CSV，完成映射、校验和入库。
5. 确认看板、年级对比、学生档案数据正确。
6. 刷新学生详情等深层路由，确认 Caddy 回退到 `index.html`。
7. 退出登录，再次访问业务页应回到登录页。

### 11.3 导入文件持久化

```bash
ls -ld /srv/scorelens/data/uploads
find /srv/scorelens/data/uploads -maxdepth 1 -type f | head
```

导入文件应位于 API 配置的持久化目录，不在 Web 静态目录中。

## 12. 日常运维

### 12.1 常用命令

```bash
# API 状态与日志
sudo systemctl status scorelens-api --no-pager
sudo journalctl -u scorelens-api --since "30 minutes ago"

# 重启 API
sudo systemctl restart scorelens-api

# 数据库状态
cd /srv/scorelens/app
docker compose ps
docker compose logs --tail 100 postgres

# 磁盘使用
df -h /srv/scorelens
du -sh /srv/scorelens/data/uploads /srv/scorelens/backups
```

### 12.2 会话与上传文件

- Session 保存在 PostgreSQL `user_sessions` 表，随数据库一起备份。
- 更换 `SESSION_SECRET` 或重启会话清理后，用户需要重新登录。
- 上传文件按 UUID 命名，不能通过 Web 根目录直接访问。
- 原始文件与数据库备份应配套保留，否则导入历史中的文件路径可能失效。

## 13. 备份与恢复

### 13.1 每日备份

先确保备份目录存在且 `scorelens` 用户可写：

```bash
sudo install -d -o scorelens -g scorelens -m 750 /srv/scorelens/backups
```

以应用账号执行数据库和上传文件备份：

```bash
sudo -iu scorelens
cd /srv/scorelens/app
STAMP=$(date +%Y%m%d-%H%M%S)
docker exec scorelens-postgres pg_dump -U scorelens -d scorelens -Fc \
  > "/srv/scorelens/backups/scorelens-${STAMP}.dump"
tar -czf "/srv/scorelens/backups/scorelens-uploads-${STAMP}.tar.gz" \
  -C /srv/scorelens data/uploads
sha256sum "/srv/scorelens/backups/scorelens-${STAMP}.dump" \
  "/srv/scorelens/backups/scorelens-uploads-${STAMP}.tar.gz" \
  > "/srv/scorelens/backups/scorelens-${STAMP}.sha256"
```

建议通过 cron 或学校现有备份任务每日执行，并设置 30 天保留策略。重要备份应再复制到 NAS 或异地，不要只保留在同一块磁盘。

### 13.2 恢复前提

恢复会覆盖数据库和上传文件，属于高风险操作：

1. 在隔离环境或确认可停机的维护窗口执行；
2. 先保存当前数据库和上传文件；
3. 确认备份文件完整且校验通过；
4. 恢复后重新执行健康检查和角色回归。

### 13.3 恢复示例

停止 API，避免恢复期间写入：

```bash
sudo systemctl stop scorelens-api
```

恢复数据库（将备份文件名替换为实际文件）：

```bash
sudo -iu scorelens
docker exec -i scorelens-postgres pg_restore \
  -U scorelens -d scorelens --clean --if-exists \
  < /srv/scorelens/backups/scorelens-YYYYMMDD-HHMMSS.dump
```

恢复上传文件：

```bash
sudo -iu scorelens
tar -xzf /srv/scorelens/backups/scorelens-uploads-YYYYMMDD-HHMMSS.tar.gz \
  -C /srv/scorelens
```

恢复后执行：

```bash
pnpm --filter @scorelens/api prisma:deploy
sudo systemctl start scorelens-api
curl -fsS http://127.0.0.1:3100/api/v1/health
```

> `pg_restore --clean` 会删除备份中包含的对象。不要在未确认目标库的情况下执行。若恢复到空库，可省略 `--clean --if-exists`。

## 14. 版本升级

### 14.1 升级前

1. 记录当前版本：`git describe --tags --always`。
2. 备份数据库与上传文件。
3. 检查服务器是否有未提交配置；不要把 `.env` 提交到仓库。
4. 阅读新版本迁移和更新说明。

### 14.2 升级步骤

```bash
sudo -iu scorelens
cd /srv/scorelens/app
git status --short
git fetch --tags
git checkout v0.2.0
pnpm install --frozen-lockfile
pnpm --filter @scorelens/api prisma:generate
pnpm --filter @scorelens/api prisma:deploy
pnpm typecheck
pnpm build
```

实际升级时将 `v0.2.0` 替换为目标版本。然后：

```bash
sudo systemctl restart scorelens-api
curl -fsS http://127.0.0.1:3100/api/v1/health
```

Caddy 直接读取最新构建目录，静态资源更新后执行：

```bash
sudo systemctl reload caddy
```

### 14.3 回滚

数据库迁移可能无法通过代码回滚撤销。优先采用：

1. 停止写入；
2. 恢复升级前数据库备份；
3. 切回上一版本代码；
4. 使用上一版本依赖和构建产物重启；
5. 完整验证登录、导入和看板。

不要把 `git reset --hard` 当作常规回滚手段，它会丢弃服务器上的本地修改。

## 15. 故障排查

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| API 无法启动 | `journalctl -u scorelens-api` | 检查 `.env`、Node 版本、dist 是否存在、端口占用 |
| 健康检查 `db=down` | `docker compose ps`、数据库日志 | 启动 PostgreSQL，检查连接串和密码 |
| 页面能打开但接口 502 | API systemd 状态 | 启动/重启 `scorelens-api`，确认 3100 仅本机监听 |
| 登录后立即退出 | `APP_ORIGIN`、HTTPS、Cookie | Origin 与实际域名一致，生产必须 HTTPS |
| Cookie 不保存 | `NODE_ENV` 与协议 | 生产使用 HTTPS；不要通过 HTTP 使用 Secure Cookie |
| 刷新 404 | Caddy 配置 | 确认 SPA `try_files {path} /index.html` 生效 |
| 上传后文件消失 | `UPLOAD_DIR` 权限和 systemd 配置 | 使用绝对路径并加入 `ReadWritePaths` |
| 中文 CSV 乱码 | 文件编码 | 当前未实现自动编码识别，优先另存为 UTF-8 CSV 或 `.xlsx` |
| Prisma 迁移失败 | 迁移状态、数据库连接 | 备份后检查 `_prisma_migrations`，不要手动删除记录 |
| 构建失败 | Node/pnpm 版本、lockfile | 使用 Node 24、pnpm 12.4.1、`--frozen-lockfile` |
| 磁盘持续增长 | PostgreSQL、上传文件、备份 | 制定上传文件和备份保留策略，检查 WAL/归档配置 |

端口检查：

```bash
sudo ss -ltnp | grep -E ':(80|443|3100|5432)\b'
```

预期 3100 和 5432 只显示本机绑定，80/443 对外提供服务。

## 17. 后续容器化方向

当前部署先把单机链路跑稳。后续如果需要完整 Docker Compose，应至少补充：

- `apps/api/Dockerfile`：多阶段构建、非 root 运行、Prisma 引擎；
- Web 静态站点镜像或继续使用 Caddy；
- API 健康检查和持久化上传卷；
- 独立数据库网络，不发布数据库端口；
- 备份容器或宿主定时任务；
- 固定镜像版本和上一版本回滚镜像。

在这些文件补齐前，不应把“完整 Compose 部署”写成当前可用能力。
