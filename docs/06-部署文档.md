## 1. 部署方式

Ubuntu 24.04 服务器只需要安装 Docker Engine 和 Docker Compose 插件，不需要安装 Node.js、pnpm、PostgreSQL 或 Caddy。

v0.4.0 起数据库为容器卷内的 SQLite 单文件，不再有独立数据库容器：

```text
教师浏览器
   │ HTTPS / HTTP
   ▼
Web 容器（Caddy :80/:443）
   ├─ 静态文件 → Vue 构建产物
   └─ /api/*   → API 容器 :3100
                    │
                    ▼
              API 容器（NestJS）
              启动时自动执行 Prisma 迁移
                    │
                    ▼
              app_data 卷
              ├─ scorelens.db     （SQLite，唯一数据源）
              └─ uploads/         （原始成绩文件）
```

仓库根目录执行：

```bash
docker compose up -d --build
```

即可启动 API 和 Web 两个服务。

## 2. 服务器要求

| 项目 | 建议 |
| --- | --- |
| 操作系统 | Ubuntu 24.04 LTS |
| CPU / 内存 | 2 vCPU / 2GB 起（SQLite 不需要独立数据库进程） |
| 磁盘 | 20GB SSD 起，按备份保留量增加 |
| 网络 | 固定内网 IP 或域名；只开放 SSH、80、443 |
| 软件 | Docker Engine + Docker Compose 插件 |
| 浏览器 | 近两年 Chrome/Edge |

API 端口不发布到宿主机，只允许 Web 容器通过 Docker 内部网络访问；SQLite 文件位于 `app_data` 卷内，不存在数据库监听端口。

## 3. 安装 Docker

以下命令使用 root 或具有 sudo 权限的账号执行。

```bash
sudo apt-get update
sudo apt-get upgrade -y
sudo apt-get install -y ca-certificates curl git ufw

sudo apt-get install -y docker.io docker-compose-v2
sudo systemctl enable --now docker

docker --version
docker compose version
```

确认当前账号可以执行 Docker 命令。若提示权限不足，可把可信账号加入 docker 组并重新登录：

```bash
sudo usermod -aG docker "$USER"
```

> Docker 组权限近似 root 权限，只应授予可信账号。

```bash
cd /opt

cd scorelens
```

如果代码已经存在，不要重复克隆，先进入项目目录并检查工作区：

```bash
cd /opt/scorelens
git status
```

## 5. 配置环境变量

复制根目录示例：

```bash
cd /opt/scorelens
cp .env.example .env
chmod 600 .env
nano .env
```

生产配置示例：

```env
SESSION_SECRET="替换为 openssl rand -hex 32 的结果"
APP_ORIGIN="https://scorelens.example.com"
SITE_ADDRESS="scorelens.example.com"
COOKIE_SECURE="true"
HTTP_PORT="80"
HTTPS_PORT="443"
```

生成随机值：

```bash
openssl rand -hex 32
```

变量说明：

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `SESSION_SECRET` | 是 | Session 签名密钥；更换后现有登录会话失效 |
| `APP_ORIGIN` | 是 | 教师实际访问的站点 Origin，必须与浏览器地址一致 |
| `SITE_ADDRESS` | 是 | Caddy 站点地址；域名用于自动 HTTPS，`:80` 表示本机 HTTP 测试 |
| `COOKIE_SECURE` | 是 | HTTPS 设为 `true`；仅限本机 HTTP 测试时设为 `false` |
| `HTTP_PORT` | 否 | 宿主机 HTTP 端口，默认 80 |
| `HTTPS_PORT` | 否 | 宿主机 HTTPS 端口，默认 443 |
| `AI_ENABLED` | 否 | 是否启用 AI 表头识别，默认 `false` |
| `AI_BASE_URL` | 否 | OpenAI 兼容接口地址，默认 `https://api.deepseek.com/v1` |
| `AI_API_KEY` | 否 | 接口密钥；为空时自动降级为规则建议 |
| `AI_MODEL` | 否 | 模型名，默认 `deepseek-chat` |
| `AI_TIMEOUT_MS` | 否 | 单次识别超时，默认 25000 |

> `DATABASE_URL` 不需要在 `.env` 中配置：`docker-compose.yml` 已固定为 `file:/app/data/scorelens.db`，指向持久化卷。
> AI 相关变量会原样传入 API 容器；不配置 `AI_API_KEY` 时，导入页仍按规则建议完成映射，不会报错。

注意：

- `.env` 已被 Git 忽略，不要提交到仓库。
- 正式环境必须使用 HTTPS，并将 `COOKIE_SECURE` 设为 `true`。
- 不要把 Session 密钥写入前端代码。

## 6. 启动全部服务

首次启动前准备备份目录，并让容器内的 `node` 用户（uid 1000）可写：

```bash
cd /opt/scorelens
mkdir -p backups
sudo chown -R 1000:1000 backups
```

启动：

```bash
docker compose up -d --build
```

查看状态：

```bash
docker compose ps
```

查看启动日志：

```bash
docker compose logs -f api web
```

启动过程：

1. API 镜像构建；
2. API 容器自动执行 `prisma migrate deploy`，在 `app_data` 卷内创建或升级 `scorelens.db`；
3. API 启动并通过 `/api/v1/health` 健康检查；
4. Web 镜像构建；
5. Caddy 启动、反向代理 API，并通过首页健康检查。

首次构建需要下载基础镜像和依赖，耗时取决于网络。

### 7.1 正式环境：创建管理员账号（不跑种子）

全新部署的 SQLite 只有表结构、**没有任何账号**，此时登录会提示“账号或密码错误”。正式环境应使用管理员初始化脚本，而不是 `seed.ts`（后者会清空全部数据）：

```bash
cd /opt/scorelens
docker compose exec \
  -e ADMIN_USERNAME=principal \
  -e ADMIN_PASSWORD='替换为至少 8 位的强密码' \
  api ./apps/api/node_modules/.bin/tsx ./apps/api/scripts/create-admin.ts
```

输出 `已创建管理员：principal` 后即可登录。该脚本可重复执行：账号不存在时创建，已存在时重置密码并补上管理员角色。

也可在本机（非容器）环境执行：

```bash
ADMIN_USERNAME=principal ADMIN_PASSWORD='替换为强密码' pnpm admin:create
```

> 若确认是测试环境，也可以直接执行第 7 节的种子脚本，但会**清空现有数据并重建演示账号**。

### 7.2 AI 表头识别配置（管理员界面）

v0.6.0 起不需要再改 `.env` 重启：管理员登录 → 系统设置 → AI 表头识别，填写接口地址（Base URL）、模型、API Key 与超时，点「测试连接」验证后「保存配置」即可，导入立即生效。

- 配置保存在 SQLite 的 `app_settings` 表中，API Key 以 AES-256-GCM 加密，页面只显示掩码；密钥由 `SESSION_SECRET` 派生，**更换 SESSION_SECRET 后需要重新填写 Key**。
- 优先级：界面配置 > 环境变量（`AI_*`）。点「恢复环境变量配置」会删除界面配置。
- 容器部署时无需额外挂载；`docker-compose.yml` 仍会把 `AI_*` 透传给容器，作为未配置界面时的兜底。
- 出网限制：容器需要能访问所填的接口地址。校内服务器不能直连外网时，把 Base URL 指向内网代理或自建 OpenAI 兼容服务。

### 7.3 标准模板与学校成绩表

- 成绩导入页「下载标准模板」会生成 xlsx（标题行 + 学号/姓名/各科分数/总分/班级排名/年级排名 + 示例行 + 填写说明）。
- 学校系统导出的成绩表**可直接上传**：系统识别“科目 + 分数/校名次/班名次”的多级合并表头，自动忽略学校、班级、序号与原始名次列；排名由系统按成绩重新计算。
- 模板中的“总分/班级排名/年级排名”列可留空，填写也只作参考，不会覆盖系统计算结果。

## 9. HTTPS 与 Caddy

Caddy 已打包在 Web 镜像中，不需要在宿主机安装。

### 9.1 域名 + 自动证书

服务器满足以下条件时，Caddy 会自动申请和续期证书：

- 域名解析到服务器公网 IP；
- 80/443 端口可访问；
- 安全组和防火墙允许 80/443；
- `.env` 中 `SITE_ADDRESS` 使用域名；
- `APP_ORIGIN` 使用 `https://域名`；
- `COOKIE_SECURE=true`。

证书存储在 `caddy_data` 卷中，容器重建不会丢失。

### 9.2 推荐：内网 IP + 纯 HTTP（无需证书）

校内服务器通常没有公网域名，也没有可被浏览器信任的证书。此时**统一使用 HTTP + IP 访问**是最省事的方案：Caddy 只监听 80 端口做反向代理与静态资源，不涉及 TLS，因此不存在证书、SNI、跳转等问题。

`.env` 配置（端口按实际空闲端口调整）：

```env
HTTP_PORT="8083"          # 宿主机访问端口，需与下方 APP_ORIGIN 一致
HTTPS_PORT="8443"         # 纯 HTTP 模式下不使用，仅占位，填一个空闲端口即可
SITE_ADDRESS=":80"        # 关键：容器内只监听 80 的 HTTP
APP_ORIGIN="http://10.113.1.238:8083"
COOKIE_SECURE="false"     # HTTP 下必须为 false，否则浏览器不保存登录 Cookie
```

```bash
docker compose up -d --force-recreate web api
curl -sI http://10.113.1.238:8083 | head -3   # 期望 HTTP/1.1 200 OK
```

访问地址：`http://10.113.1.238:8083`。

配置要点：

- `SITE_ADDRESS` 必须是 `:80`（容器内监听端口）。写域名或 IP 会让 Caddy 走 HTTPS，用 HTTP 访问就会 308 跳转或握手失败。
- `HTTPS_PORT` 在纯 HTTP 模式下不会被使用，但 compose 仍会尝试绑定它——**它必须是空闲端口**，否则 web 容器启动报 `port is already allocated`。
- `APP_ORIGIN` 只用于 CORS 白名单。本系统前后端同源（同端口经 Caddy 反代），正常访问不经过 CORS，因此端口写错不会导致登录失败；但通过 Vite 开发端口直连 API 时需要写对。
- 浏览器若仍提示「不安全」或 `ERR_SSL_PROTOCOL_ERROR`，说明浏览器把地址升级成了 https，处理方式见 17.2。

> HTTP 明文在校园内网可接受，但密码与成绩在传输中不加密。若日后需要 HTTPS，按 9.3 用内部 CA，或申请域名走 9.1。

### 9.3 可选：无公网域名的内网 HTTPS（Caddy 内部 CA）

> 仅在确实需要 HTTPS 时使用；日常校内使用建议保持 9.2 的纯 HTTP 模式。

校内服务器通常没有公网域名，而用 `http://IP:端口` 访问又会被 Chrome 的“一律使用安全连接”拦截（表现为 `ERR_SSL_PROTOCOL_ERROR`）。Caddy 对 **IP 地址、`localhost`、`.local` / `.internal` / `.home.arpa` 主机名**会自动使用内置 CA 签发证书，因此不申请公网证书也能得到浏览器认可的 HTTPS，只需在客户端导入一次 Caddy 根证书。

服务器端：

```bash
# 1. 确认 80/443 空闲（被占用时先停掉占用方，见 17.1）
sudo ss -ltnp | grep -E ':(80|443)\b'

# 2. 修改 .env：证书主体直接用服务器 IP，无需 DNS 与 hosts
# SITE_ADDRESS="10.113.1.238"
# APP_ORIGIN="https://10.113.1.238"
# COOKIE_SECURE="true"
# HTTP_PORT="80"
# HTTPS_PORT="443"
# 裸 IP 访问 HTTPS 时客户端不发送 SNI，必须指定默认证书名，否则握手报 internal error
# TLS_DEFAULT_SNI="10.113.1.238"

# 3. 重建 Web 容器（Caddy 会生成内部 CA 并为该 IP 签发证书）
docker compose up -d --force-recreate web

# 4. 导出根证书，供客户端导入
docker compose cp web:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt
```

**为什么还要设置 `TLS_DEFAULT_SNI`**：浏览器和 curl 访问 `https://IP` 时**不会发送 SNI**，Caddy 拿不到主机名就无法选择证书，握手直接以 `tlsv1 alert internal error` 结束——此时日志里仍会显示 `certificate obtained successfully`，容易误判。因此 `docker/Caddyfile` 顶部增加了全局指令 `default_sni {$TLS_DEFAULT_SNI:localhost}`，用 `TLS_DEFAULT_SNI` 指定默认证书名（与 `SITE_ADDRESS` 的 IP 保持一致）。

Caddyfile 现由 `./docker/Caddyfile` 直接挂载进容器，调整站点或证书配置后只需重建容器，无需重新构建镜像：

```bash
docker compose up -d --force-recreate web
```

验证（`-k` 表示暂不校验证书，先确认 TLS 已通）：

```bash
curl -kI https://10.113.1.238
# 期望：HTTP/2 200，server: Caddy
```

Windows 客户端（以管理员身份打开 PowerShell，把根证书导入“受信任的根证书颁发机构”）：

```powershell
certutil -addstore -f Root .\caddy-root.crt
```

导入后直接用浏览器访问 `https://10.113.1.238`（不要再带 8083 / 8443 等端口），地址栏应显示安全锁，不再出现“不安全”提示。客户端只需操作一次，换电脑时重复导入即可。

注意事项：

- **443 必须映射到容器 443**。Caddy 的 HTTP→HTTPS 跳转固定指向 443，只发布 `8443` 时跳转会落到未监听的端口。
- 证书主体是 `SITE_ADDRESS`。虚拟机用 DHCP 更换 IP 后需改 `SITE_ADDRESS` 并重建；建议给虚拟机配置静态 IP，或改用内网域名（如 `scorelens.local`，需在客户端 hosts / DNS 中解析到该 IP）。
- 内部 CA 保存在 `caddy_data` 卷中。删除该卷会重新生成 CA，所有客户端需重新导入新的根证书。
- 只分发 `root.crt`，不要外传 `root.key`（CA 私钥在服务器上，属敏感文件）。

## 10. 防火墙

确认 SSH 连接正常后：

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
```

只需开放 80/443。API 端口 3100 不发布到宿主机，SQLite 也没有网络监听端口。

## 12. 数据持久化

Compose 使用以下卷与目录：

| 卷 / 目录 | 用途 | 删除后果 |
| --- | --- | --- |
| `app_data` 的项目前缀卷 | `scorelens.db` + `uploads/` | 学生、考试、成绩与原始文件全部丢失 |
| 宿主机 `./backups`（绑定挂载） | SQLite 快照 | 仅影响历史备份 |
| `caddy_data` | HTTPS 证书 | 下次启动重新申请证书 |
| `caddy_config` | Caddy 运行配置 | 通常可自动重建 |

查看实际卷名：

```bash
docker volume ls
```

停止服务但保留数据：

```bash
docker compose down
```

> `docker compose down -v` 会删除命名卷。除非明确要清空所有数据，否则不要使用 `-v`。

## 13. 备份

### 13.1 备份数据库

使用容器内的备份脚本，通过 SQLite `VACUUM INTO` 生成一致性快照（服务运行中也可执行），快照直接写到宿主机 `./backups`：

```bash
cd /opt/scorelens
docker compose exec -T api ./apps/api/node_modules/.bin/tsx ./apps/api/scripts/backup-db.ts
ls -lh backups
```

> 不要直接 `cp` 正在写入的 `scorelens.db`：SQLite 默认使用回滚日志，热拷贝可能得到撕裂的文件。

### 13.2 备份上传文件

```bash
STAMP=$(date +%Y%m%d-%H%M%S)
docker compose exec -T api tar -czf - -C /app/data uploads \
  > "backups/scorelens-uploads-${STAMP}.tar.gz"
```

### 13.3 生成校验文件

```bash
sha256sum backups/*.db backups/*.tar.gz > backups/scorelens-checksums.sha256
```

建议每日执行（可写进宿主 cron），保留 30 天，并复制到 NAS、移动硬盘或网盘。备份未做过恢复验证，不能视为可靠备份。

## 14. 恢复

恢复会覆盖数据库，属于高风险操作。先在维护窗口停止业务写入，并保存当前数据（先按第 13 节做一次备份）。

### 14.1 停止 API

```bash
cd /opt/scorelens
docker compose stop api
```

### 14.2 覆盖数据库文件

```bash
docker compose run --rm --no-deps --entrypoint sh api -c \
  'cp /app/backups/scorelens-YYYYMMDD-HH-MM-SS.db /app/data/scorelens.db'
```

> 该命令沿用 API 服务的卷配置，`./backups` 与 `app_data` 都会挂载；快照文件需已存在于 `./backups`。
> 如快照来自其他机器，先把文件放进 `./backups` 再执行。

### 14.3 恢复上传文件（可选）

```bash
docker compose run --rm --no-deps --entrypoint tar api -xzf - -C /app/data \
  < backups/scorelens-uploads-YYYYMMDD-HHMMSS.tar.gz
```

### 14.4 启动并验证

```bash
docker compose start api
docker compose ps
curl -fsS http://127.0.0.1/api/v1/health
```

按四类角色重新登录回归，并抽查导入文件、考试和成绩。

## 15. 升级

### 15.1 升级前

1. 执行一次备份：`docker compose exec -T api ./apps/api/node_modules/.bin/tsx ./apps/api/scripts/backup-db.ts`；

## 17. 故障排查

| 现象 | 优先检查 | 处理 |
| --- | --- | --- |
| API 容器反复重启 | `docker compose logs api` | 检查迁移日志、`app_data` 卷写权限、`SESSION_SECRET` 是否为空 |
| 健康检查 `db=down` | `/app/data` 目录、卷挂载 | 确认卷已挂载且容器内 `node` 用户可写；必要时删除卷后重新迁移（会丢数据） |
| 备份脚本报权限错误 | `./backups` 属主 | `sudo chown -R 1000:1000 backups` 后重试 |
| `database is locked` | 并发写入 | 单班部署下极少出现；确认没有多个 API 容器同时挂载同一卷 |
| Web 502 | API 容器状态 | 等待 API 健康，确认 `api:3100` 可解析 |
| 页面打开但接口失败 | 浏览器 Network、`APP_ORIGIN` | Origin 必须与访问地址完全一致 |
| 登录后立即退出 | HTTPS、`COOKIE_SECURE` | 生产使用 HTTPS + `COOKIE_SECURE=true` |
| HTTP 测试无法登录 | Cookie Secure | 仅本机测试设置 `COOKIE_SECURE=false` |
| 证书申请失败 | 域名解析、80/443、防火墙 | 放行端口并确认域名指向服务器 |
| 构建失败 | Docker 日志、lockfile | 使用仓库锁文件，清理旧镜像后重建 |
| 上传文件丢失 | `app_data` 卷 | 确认没有执行 `down -v`，从备份恢复 |
| 磁盘持续增长 | `backups`、容器日志 | 制定保留策略并清理旧快照 |
| 启动报 `Bind for 0.0.0.0:8080 failed: port is already allocated` | 宿主机端口被其他进程或旧容器占用 | 见 17.1：先定位占用方，再换端口或停掉占用方 |

### 17.1 端口被占用（Bind for 0.0.0.0:PORT failed）

现象：`api` 已是 `Healthy`，但 `web` 启动失败并提示 `port is already allocated`。原因是 Web 容器要把宿主机的 `HTTP_PORT` / `HTTPS_PORT` 映射到容器，而该端口已被别的进程或旧容器占用；与镜像构建、数据库无关。

先定位占用方（把 8080 换成报错里的端口）：

```bash
# 宿主机上谁在监听
sudo ss -ltnp | grep ':8080'

# 是否有容器占着该端口
docker ps --format 'table {{.Names}}\t{{.Ports}}\t{{.Status}}' | grep 8080

# 是否有残留的编排项目
docker compose ls -a
```

按情况处理，三种方式任选其一：

1. **换端口（推荐，影响最小）**：修改 `.env` 的 `HTTP_PORT`（如 8081），并同步 `APP_ORIGIN`，然后只重建 Web：

   ```bash
   nano .env          # HTTP_PORT=8081；APP_ORIGIN="http://服务器IP:8081"
   docker compose up -d web
   ```

2. **停掉占用方**：若确认是其他服务（如 nginx、旧的应用）占用，先停止该服务；若是历史遗留的容器：

   ```bash
   docker ps -a | grep 8080
   docker stop <容器名> && docker rm <容器名>
   docker compose up -d web
   ```

3. **清理旧的编排项目**：同一目录多次改名或复制部署过时，旧项目会继续占端口：

   ```bash
   docker compose ls -a
   docker compose -p <旧项目名> down
   docker compose up -d
   ```

注意：

- 改完端口必须同步 `APP_ORIGIN`，否则登录请求会因 Origin 不一致被拒绝。
- 仅测试环境可设 `COOKIE_SECURE=false`；正式环境请用 HTTPS 域名并把 80/443 留给 Caddy。
- `docker compose up -d web` 只会重建 Web 容器，`api` 与数据卷不受影响。

### 17.2 用 IP + 端口访问提示“不安全 / 无法建立安全连接”

现象：容器全部 Up，`curl http://IP:端口` 却返回 308 跳转到 `https://域名`，浏览器提示 `ERR_SSL_PROTOCOL_ERROR` 或“此网站无法提供安全连接”。

原因通常是以下三种之一：

1. **`SITE_ADDRESS` 仍是域名**：Caddy 为该域名申请证书并强制 HTTPS 跳转，而 8083 映射的是容器 80；
2. **浏览器把地址自动升级成了 `https://IP:8083`**（之前访问过 HTTPS，或手动输入了 https）；
3. **端口映射错位**：把 `HTTP_PORT` 映射到了容器 `443`。

排查：

```bash
grep -E 'SITE_ADDRESS|APP_ORIGIN|COOKIE_SECURE|HTTP_PORT' .env
curl -I http://10.113.1.238:8083            # 正常应返回 200
docker compose logs --tail 30 web           # 是否出现 certificate / redirect 相关日志
docker compose port web 80                  # 确认宿主机端口映射到容器 80
```

处理顺序（先服务端、再浏览器）：

1. 服务端切纯 HTTP（见 9.2）：

```bash
cd /opt/scorelens
sed -i 's|^SITE_ADDRESS=.*|SITE_ADDRESS=":80"|'      .env
sed -i 's|^COOKIE_SECURE=.*|COOKIE_SECURE="false"|'  .env
docker compose up -d --force-recreate web
curl -sI http://10.113.1.238:8083 | head -3          # 必须 200，若仍 308 回到第 1 步
```

2. 浏览器不再自动升级为 https（Chrome / Edge）：

- 地址栏输入**完整**地址 `http://10.113.1.238:8083`，不要只写 `10.113.1.238:8083`；
- `chrome://settings/security` → 关闭「始终使用安全连接」；
- `chrome://net-internals/#hsts` → *Delete domain security policies* 输入 `10.113.1.238` → Delete；
- 清除该站点数据（`chrome://settings/content/all` 搜索该 IP → 删除），避免点历史记录时仍跳到旧的 https 地址。

3. 交叉验证：`curl.exe -I http://10.113.1.238:8083`（Windows）能拿到 200，而浏览器仍失败，即确定为浏览器策略问题。

> 需要 HTTPS 时的可行路径见 9.1（公网域名 + 自动证书）与 9.3（内网主机名/IP + Caddy 内部 CA，客户端导入根证书）。用 IP 自签证书而不导入根证书，浏览器同样会拦截。

进入容器检查数据库：

```bash
docker compose exec api ls -lh /app/data
docker compose exec api sh -c 'echo $DATABASE_URL'
```

需要查看表数据时用 Prisma Studio（本机开发）：
`pnpm db:studio`，不要在服务器上长期开放 Studio 端口。
